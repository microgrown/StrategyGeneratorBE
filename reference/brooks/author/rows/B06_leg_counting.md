## Flagged, authored anyway

- `LegCountAtLeast` and `PullbackDurationBars` were merged with `sides: same`. Both were authored MIRRORED. Both read a directional anchor — the high counter / a fresh N-bar high on the long side, the low counter / a fresh N-bar low on the short — and copying the long text into the short slot is precisely the failure the authoring skill names. The merged `sides` field is the only thing deviated from; the conditions themselves are the merged pseudocode.
- `FirstPullbackAfterSpike` gained one input the merge did not list, `bodyFraction(0.6)`, because "strong bull trend bar" has no numeric content otherwise and the settled spike decision points at `StrongTrendBarRun`, whose definition it is. It must be pinned or optimized like any other body-fraction input.
- `FirstPullbackDelay` deviates from the merged pseudocode's `lowest(low, b)[1]` in SPELLING only, carrying the same value as a running minimum. `b` is unbounded before the first breakout of a run and the literal window would index past Max Bars Back; the running minimum is identical in value and bounded by `breakoutLookback`.
- `SecondSignal`'s failure window is the `k - 1` bars ENDING AT THE CURRENT BAR, exactly as the merged pseudocode spells it, which is why the scan starts at `k = 2`. It omits bar `k - 1` (the bar right after the first trigger); that is the merge's spelling and is left as-is rather than silently widened.
- Cross-slice: `HighThreeEntry` (B03, three_push_patterns) is described as "buy when the high/low bar counter just advanced to 3", which is `HighLowBarCount` at `countTarget = 3` — an existing rule at a fixed parameter. B06 authors the counter as instructed; B03's rule is the duplicate and should be dropped or given a term the counter does not carry. `CounterSignalReversalPermission` (B12) reads the same opposing counter as `OpposingCountExit` but as an Entry permission while holding a countertrend position, so it is not the same rule.
