Since that merge, `rules/TrendDurationBars.json` was authored and IS exactly that gate: an Entry, identical both sides, holding the settled always-in state machine (flip on `consecutiveBars` consecutive strong trend bars, body ≥ `bodyFraction`, both tails ≤ `tailFraction`, undefined until the first flip) and firing when `aiDir != 0 and aiBars >= minTrendBars`. Entry panes AND, so `ClimaxBar(climaxMultiple 1.5, atrLength 10, bodyFraction 0.6)` placed beside `TrendDurationBars(minTrendBars 10, consecutiveBars 2)` reproduces this rule term for term — skill §2's "is it an existing rule at a fixed parameter" test, applied to a pair. The merged pseudocode adds nothing else: it does not require the climax to agree in direction with the always-in run. If the orchestrator wants it anyway, the distinguishing term would have to be that agreement, and that is a design decision this slice should not make alone.
