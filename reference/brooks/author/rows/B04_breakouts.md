# B04 breakouts — CATALOG rows

| Rule | Type | Sides | Reaches back | Inputs | Fires when |
|---|---|---|---|---|---|
| `BothSidedFailedBreakouts` | Entry | same | `reentryWindow + rangeLookback` | `rangeLookback(15)`, `reentryWindow(10)` | A failed breakout has occurred on BOTH sides of the range inside the same window: some bar in the last `reentryWindow` bars closed below the lowest low of the `rangeLookback` window ending one bar before it and this bar closed back above that level, AND the mirrored thing happened on the highs. Bears trapped below and bulls trapped above, so the next genuine breakout is expected to travel further. Not a composition of two placements: the pane system ANDs entry rules but each placement carries ONE side, so "the long-side failure and the short-side failure, both on this bar" cannot be stacked out of two `FailedBreakoutReversal` placements — the same reason `NumBarsIfProfitable` cannot be built from `NumBars` plus a profit rule. That rule's loop is inlined verbatim (per-candidate level open-coded, since `Lowest(l, N)[kk + 1]` is a function-history reference at a VARIABLE offset) rather than a second spelling being invented. Direction-agnostic, so both sides carry the same text |
| `FailedSwingBreakoutReversal` | Entry | mirrored | `lookback - 1 + strength` | `strength(2)`, `lookback(20)` | The bar's low trades below the most recent CONFIRMED swing low and the bar closes back above it (short: the mirror at a swing high) — the swing-extreme breakout that fails. The pivot scan is inlined from `SwingHigh` per the B-list decision (strictly beyond the `strength` newer bars, at or beyond the `strength` older ones, lag exactly `strength`, `-1` sentinel guarded, `el_gt`/`el_ge` for the relational tolerance); the twin reads the same pivot as a price through `SwingLow`/`SwingHigh`. The pivot is read AT THE CURRENT BAR, not lagged: the newest pivot the scan can return sits `strength` bars back and must be strictly below bar 0, so it can never be the one broken — which delivers the merged pseudocode's `[1]` without the unmeasured lagged function read `SwingLow(...)[1]`. Not `StopRunReversalBar` (a plain window extreme, the PRIOR bar breaks) and not `SmallBreakoutTrapReversal` (window extreme, capped break) |
| `SecondFailedSwingBreakoutReversal` | Entry | mirrored | `swingLookback - 1 + strength` | `lookback(20)`, `strength(2)`, `swingLookback(20)` | At least the SECOND failed swing-extreme breakout within `lookback` bars — Brooks's second attempt to reverse, the one more likely to work. `FailedSwingBreakoutReversal`'s condition is inlined and counted by a PERSISTENT AGE COUNTER, not `CountIF`: `CountIF`'s condition is a true series whose offsets shift per counted bar, so counting this event would evaluate `SwingLow(...)[i]` at every offset in the window and the lagged read of a swing function has no register row. The age is advanced before the test and reset after it, so it is the bars since the PREVIOUS event, 1 at the earliest, matching "some earlier bar i in 1..lookback"; the counter starts at 0/false exactly as the EL variables do, so nothing is claimed before an event has printed. `swingLookback` promoted — the merged parameters gave no pivot window |
| `OpeningRangeBreakout` | Entry | mirrored | `1` (plus the session state carried in locals) | `openingBars(8)`, `firstCrossOnly(0)` | Once the first `openingBars` bars of the session have fixed the opening range, a bar closes above its high (long) / below its low (short). Not `Breakout` or `HighestHighBreakout`, whose Donchian window MOVES with every bar — the opening-range level is FIXED for the whole session once set, so they fire on different bars from mid-session on. Session model per the standing decision: the session starts on `date > date[1]` (`day_of(ctx.Time(0)) > day_of(ctx.Time(1))` in C++), running values and a bars-into-session counter in locals reset there; `SessionOpeningRange` is inlined, not referenced. `firstCrossOnly(1)` restricts it to the bar that FIRST crosses the level; the sources disagreed (one wants the first crossing, one a confirming second bar) and the negation of one is not the other, so the flag carries the first at default 0. The range's last bar cannot fire on itself, so the first eligible bar is `openingBars + 1`. Warm-up: locals start at 0 as the EL variables do, so a mid-session first calculated bar leaves `orLow` at 0 until the first date change — mirrored, not corrected. Intraday only |
| `ReenterAfterQuickStopOut` | Entry | same | `0` | `reentryBars(1)`, `quickBars(2)` | Flat, at least one trade closed, the most recently closed position lost (`PositionProfit(1) < 0`), the exit was at most `reentryBars` bars ago (`BarsSinceExit(1)`), and that trade was held at most `quickBars` bars — Brooks's permission to reverse straight back in. A GATE only: the direction comes from whatever entry rule shares the pane, so both sides are the same text. It is `LastTradeCooldown`'s condition in the opposite sense PLUS the quick-loss term that makes it a different rule. THE HOLDING PERIOD IS NOT AN ACCESSOR in either library — `BarsSinceEntry` answers 0 while flat (measured, never a sentinel) — so it is reconstructed in the same three statements in BOTH twins from the previous bar's `MarketPosition` and `BarsSinceEntry`: on the bar the position goes flat the trade lasted `prevBse + 1` bars. That is an elapsed-bar reconstruction only; anything about money still goes through the measured accessors. `haveHeld` keeps warm-up honest, since `lastHeld` starts at 0 and would otherwise read as the quickest possible trade |
| `SessionBarBreakout` | Entry | mirrored | `offsetBars + 1` | `offsetBars(1)` | The bar exactly `offsetBars + 1` into the session closes above the high (long) / below the low (short) of the session's FIRST bar: `Date[offsetBars] > Date[offsetBars + 1]` gates it, which turns an every-bar test into a once-a-day one. `offsetBars(1)` is the second bar of the day breaking the first bar's high, `(2)` the third bar doing it — one rule with a parameter rather than two near-identical files. Not `CloseAbovePriorHigh`, which is the price half at every bar of the chart; not `OpeningRangeBreakout`, whose level is a multi-bar range and which fires on any later bar of the session. Intraday only — on a daily series every bar is its own session and the rule degenerates to `CloseAbovePriorHigh` |
| `BothSidesShallowBreakoutFade` | Entry | mirrored | `1` (plus the session state carried in locals) | `maxExtension(0.15)` | The session already poked beyond one side of the day's range by a small amount and has now reversed and poked beyond the other side by a small amount, with a confirming bar: long is a shallow break of the session low after an earlier shallow break of the session high on a bull bar. Shallow is measured against the session's own range SO FAR taken as of the PREVIOUS bar, so the current bar cannot enlarge its own benchmark, and the test is a MULTIPLICATION rather than a ratio because EL raises a runtime divide-by-zero on a zero denominator. Session model per the standing decision (`date > date[1]`, running high/low and a bars-into-session counter in locals). Warm-up needs no guard: before the first date change the running low stays 0 so no downside poke can register and neither side fires. A two-sided cousin of `TwiceFailedBreakoutAttempt` (B05, one side, repeated) — the second break is on the OPPOSITE side, so they never fire on the same bar. Intraday only |
| `BreakoutPullbackEntry` | Entry | mirrored | `maxBarsSinceBreakout + breakoutLookback` | `breakoutLookback(10)`, `maxBarsSinceBreakout(8)`, `minPullbackBars(1)`, `maxPullbackBars(10)` | Brooks's three-stage breakout pullback: the most recent bar `k` in `1..maxBarsSinceBreakout` closed above the highest high of the `breakoutLookback` bars ending one bar before it, the pullback since then is `k - 1` bars and lies within `minPullbackBars..maxPullbackBars`, and this bar closes above the highest high of those pullback bars. Short is the mirror. The level is open-coded per candidate (`Highest(High, N)[k + 1]` is a function-history reference at a VARIABLE offset; `Extremes()` is EL source and is exactly this loop) and "most recent" is a `brkUpBar = -1` guard, because EasyLanguage has no loop break and both twins must run the same iterations. The bound is on bar COUNT, not depth: the sources allow the pullback to make either a higher or a lower low. Kept whole rather than split — the resumption leg alone is `CloseAbovePriorHighestHigh` over a window whose LENGTH is data-dependent, which no placement can express. At `minPullbackBars = maxPullbackBars = 1` it is the cheapest source form. The hold-above term is `BreakoutLevelRetest` and is not duplicated here |
| `BreakoutPullbackWindow` | Entry | mirrored | `startWindow + breakoutLookback` | `startWindow(5)`, `maxPullbackBars(5)`, `breakoutLookback(10)` | Context filter, not a signal: the most recent breakout bar is `k` bars back with `k <= startWindow`, and the pullback since it is `k - 1` bars with `1 <= k - 1 <= maxPullbackBars` — the setup on the table is a breakout PULLBACK, not a failed breakout. Same bounded backward scan and open-coded per-candidate level as `BreakoutPullbackEntry`, same `-1` guard for "most recent". Not that rule with a term dropped in the sense that matters: this fires on EVERY bar of the pullback, that one only on the bar the pullback ends. `breakoutLookback` promoted to an input at `BreakoutPullbackEntry`'s default — the sources say "a breakout" and leave the level implicit — so the two can be tuned together. The level test that separates a breakout pullback from a failed breakout is `PullbackBeyondBreakoutPoint` (B05) and is deliberately not folded in |
| `BreakoutRunsWithoutPullback` | Entry | mirrored | `confirmBars + breakoutLookback` | `scalpDistance(4)`, `confirmBars(3)`, `breakoutLookback(10)` | Filter: the most recent breakout bar is `k` bars back with `k <= confirmBars` (the scan includes bar 0, so the filter is live on the breakout bar itself), the close is now at least `scalpDistance` beyond the level that bar broke, and the lowest low from the breakout bar to now has held at or above that level. Read the move as new with-trend buying rather than a reversal setup. Kept apart from `SpikeWithoutPullback`, which is a rolling window statistic with no level at all, and from `BreakoutTestNoOverlap`, whose reference is a single bar's high and which has no distance term. `scalpDistance` is in PRICE POINTS as `BreakoutMissesScalpTarget`'s is — the source states ticks, the engine exposes no tick size to strategies, so it is instrument-specific and must be set per symbol in the grid. `breakoutLookback` promoted, as in `BreakoutPullbackWindow` |
| `CounterSpikeIntoEmaSupportEntry` | Entry | mirrored | `max(spikeBars, atrLookback + 1)` | `spikeBars(3)`, `bodyFraction(0.6)`, `emaLength(20)`, `supportAtr(0.5)`, `atrLookback(14)` | Bars `1..spikeBars` are all bear TREND bars (body at least `bodyFraction` of the bar's own range), this bar's low reaches down to within `supportAtr` ATRs of the EMA, and this bar closes up: buy the countertrend spike into the average. Short is the mirror. The run is read at bars 1..spikeBars, not 0..spikeBars-1, because the current bar closes AGAINST the spike and cannot be part of it; the run test is `StrongTrendBarRun`'s, start-true-and-clear so the loop runs unconditionally and EL's lack of short-circuiting cannot matter. Not `CloseAboveAverage`, a plain close-vs-simple-average test. The band replaces the source's tick tolerance, the ATR-fraction substitution `PriorSessionLevelTest` and `BreakoutLevelRetest` make. `WFSafe_Xaverage` (price seed on the study's first calculated bar, `X = X[1] + SF*(P - X[1])`, `SF = 2/(Length+1)`, no warm-up hole) and the `WFSafe_AvgTrueRange` rolling accumulator, one call site each in the hook. CURRENT-BAR EMA READ ONLY — the lagged read is still unmeasured. `emaLength` MUST BE PINNED in the grid: the wrapper's length-change behaviour is unmeasured. The book's "established bull trend" qualifier is dropped, not inherited |
| `FailedBreakoutOfPriorSessionExtreme` | Entry | mirrored | `1` (plus the session state carried in locals) | `maxBarsIntoSession(12)` | Intraday: within the first `maxBarsIntoSession` bars of the session the bar's low breaks below the PRIOR session's low and the bar closes back above it (short: the mirror at the prior session's high) — a failed breakout of yesterday's extreme, fired on the breakout bar itself. Kept apart from `FailedBreakoutReversal`, whose level is an N-bar window and which fires a bar or more later. The twin calls `HighD(1)`/`LowD(1)` per the standing decision; the engine exposes neither, so the C++ keeps the running calendar-day extremes, rolls them on `date > date[1]` (the same boundary the xxxD family carries) and keeps the measured `-1` sentinel as the initial value, guarded on both sides. One divergence, stated rather than hidden: TradeStation's `HighD` reads the chart's own data and answers on the first evaluated bar, while the mirror sees only bars from Max Bars Back on, so a day becomes "the prior session" only after its own first bar has been observed — the C++ is silent through the first partial day and the first fully observed day, and the two agree exactly from the second date change on. Same class as the EMA seed bar: the engine's window is part of the specification, and the mirror errs toward no signal |

## Not written

- `BreakoutFailedBackIntoRange` — suspected duplicate of `FailedBreakoutReversal`, which the merge pass did not catch (its `catalog_match` was `none`). That rule's `shortCondition` is `brokeUp`: "some bar in the last `failBars` bars closed ABOVE the high extreme of the `rangeBars` window ending one bar before it, and this bar closes back BELOW that level" — which is this candidate's long-side pseudocode word for word, so the candidate is `FailedBreakoutReversal` with the sides swapped, and side-flip is a per-placement toggle. The only real difference is that the candidate anchors ONE level at `[reentryWindow + 1]` where the corpus rule slides the level per candidate breakout bar; that changes which bars fire at the margin but not the claim. The merge note anticipated the comparison ("a breakout pullback and a failed breakout differ only in whether price closes back inside"). Brian's call: if the anchored level is wanted as a variant it needs a name that says so. `BothSidedFailedBreakouts` was authored regardless, since it needs both sides on one bar and inlines `FailedBreakoutReversal`'s loop.
- `OverlappingLargeBarCluster` — suspected duplicate plus a top-level conjunction. Its overlap half (mean adjacent-bar overlap at or above `minOverlap`) is `AverageBarOverlap` negated — that rule is the same mean pairwise overlap with `<= maxAvgOverlap`, and negation is a per-placement toggle; `OverlappingBarRun` states the all-pairs form of the same claim un-negated. What is left is an independent second condition, "the mean bar range of the last `overlapBars` bars is at least `sizeMultiple` times the mean range of the last `longerLookback`", which is not in the corpus (`AtrFastAboveSlow` is the nearest, but on WFSafe ATR with no multiplier, and `LargeRangeBarInWindow` counts single bars). Per the skill's split rule the compound is strictly worse than the negated placement plus that filter, so the recommendation is to author the missing size filter under its own key (`AvgRangeAboveLongerAvg`, say) rather than this compound. Not written pending that decision.

## Notes for the roll-up

- `SessionBarBreakout` (this slice) and `SessionFirstBarBreakout` (B05, `breakouts_volume_gap`) look like one rule restated. This one requires the bar to be EXACTLY `offsetBars + 1` into the session; B05's is "early in the session", i.e. a window. Whoever authors B05 should read this file first — at a window of 1 they are the same rule.
- `OpeningRangeBreakout` and `BothSidesShallowBreakoutFade` inline the session model that B07 will author as `SessionOpeningRange` / `IsFirstBarOfSession`. That is the standing instruction (inline the parts, keep the dependency in the row text), but if B07 changes the session model, these two follow it.
- Three rules promote a `breakoutLookback` input that the merged parameters omitted (`BreakoutPullbackWindow`, `BreakoutRunsWithoutPullback`) or a pivot window (`SecondFailedSwingBreakoutReversal`'s `swingLookback`). All are at the corresponding sibling rule's default so they can be tuned together.
