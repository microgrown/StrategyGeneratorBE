## Notes for the orchestrator

- `BarRangeAtrMultiple` was authored as the atomic rule per the slice-13 note: `ClimaxBar`'s catalog row already names it as the half it inlines, and the two now differ only by `ClimaxBar`'s strong-trend-body term. Its ATR block is a verbatim copy of `ClimaxBar`'s, which is `AtrProfitTarget`'s, including the two separate accumulator statements.
- `StrongTrendBar` is now the corpus's atomic strong-trend-bar test. Three rules already inline its body half at a hard-coded or separately-named `bodyFraction` — `ClimaxBar`, `ConsecutiveClimaxBarCount`, `LargestTrendBarOfTheRun` — and slice 10's `ExitOnOppositeStrongTrendBar` inlines body plus one tail on the opposite side. None is a duplicate (each ANDs something this rule does not have, and the exit reads position state), but if a future pass wants one definition of "strong trend bar", this is the rule to point them at.
- `BreakoutBarLargeBodyLargeRange` (slice 02) landed on disk while this slice was running and is NOT a duplicate of `StrongTrendBar`: it is direction-agnostic (`AbsValue(Close − Open)`, same both sides), has no tail terms, and ANDs a range-versus-average term this rule does not carry. A large-bodied bear bar in a bull pane passes it and fails `StrongTrendBar`; a shaved small-range bull bar does the reverse.
- Gap rules stated on daily bars (`TrueGapBar`, `LargeGapVsAverageRange`, `LargeGapVsRecentGaps`, and `PriorBarStrongTrendDay`) are written with no daily-specific machinery — no `HighD`/`LowD`, no date slicing — so they run unchanged on any timeframe. The daily-ok note is about where Brooks stated them, not a restriction in the code.
- No rule in this slice needed an unregistered EasyLanguage word. The only tick-unit parameter in the slice, `LimitEntryAtMicroGapEdge`'s `entryOffsetTicks`, was converted to `entryOffsetPoints` (price units) because `minmove` and `pricescale` are UNKNOWN.
