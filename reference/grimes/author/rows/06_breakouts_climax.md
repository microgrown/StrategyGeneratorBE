## Notes for the orchestrator

- **The second cluster, `TrendRateAcceleration` / `AcceleratingLegsClimax`, was KEPT APART**, both written. Reason: `AcceleratingLegsClimax` is SIGNED and MIRRORED — it requires the prior leg to run in the trade's own direction, which is what makes its comparison mean "steeper in the same direction" — and it PINS the two windows equal (`legBars`, `2 × legBars`). `TrendRateAcceleration` is ABSOLUTE and direction-agnostic, and cross-multiplies by the two window lengths so they may differ. No setting of either rule's inputs reproduces the other's fired-bar set (a down leg following a larger up leg fires the absolute rule and not the signed one), and neither the negate nor the flip toggle bridges them. A boolean that switched BOTH the sign requirement AND the meaning of the short side is a larger switch than merge decision 12's one-line-ratio case covers, and it would make the grid unreadable — the same placement would mean a different thing on the short side depending on the boolean.
- `AcceleratingLegsClimax` is `ParabolicAccelerationExit`'s arithmetic term for term in the Entry role (defaults 5/1.5 against 4/1.5). That is a deliberate role twin, settled by the merge pass with the `ConsecutiveCloseExit` / `MomentumConsecutiveBars` precedent, not a duplicate the merge missed — flagged here so it is a conscious keep.
- `BreakoutBarRangeAndVolumeExpansion` is the slice's only deliberate compound. Positively placed it is reachable as two panes (`BarRangeBelowAverageMultiple` negated + `VolumeAboveAverageMultiple`); the file exists for the NEGATED placement, which no pair of ANDed panes can express.
- `BreakoutBarRangeAndVolumeExpansion` carries two non-`int`/`double`/`bool` locals (`volHistory` as `std::vector<double>`, `volCursor` as `std::size_t`) — `VolumeAboveAverageMultiple`'s ring-buffer machinery verbatim, and the same `validateRule` "unusual local type" warning it raises. Everything else in the slice validates and lints clean with no warnings.
- Grid note for `ShrinkingConsecutiveBarRanges` and `ShavedTopBar`: both run-length inputs are vacuously true at 1 (`ShavedTopBar` at 1 is the single-bar rule, which is intended; `ShrinkingConsecutiveBarRanges` at 1 fires on every bar), so that rule's `barCount` grid should start at 2.
- `LevelTouchCount`'s `maxTouches` grid must include 0 (unbounded) to keep the existing floor-only reading reachable; `ChannelLineBreakTrendBarClose`'s `breakMarginAtr` likewise must include 0.
