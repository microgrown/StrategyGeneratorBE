## Amended

_None._ No rule in this slice was a parameterization on re-check: every `catalog_match` was `variant`, and each held up against the named rule's actual JSON (see "Catalog re-checks" below).

## Catalog re-checks

Each `catalog_match` was re-read against the rule's JSON on disk before authoring, with the parameterization option considered first:

- `ThreePushAcceleration` vs `ThreePushSymmetry` — confirmed a one-sided multiple on the two increments; no setting expresses "about equal", and no `ThreePush*` rule measures time symmetry (`ThreePushDurationWindow` bounds TOTAL bars). Not a parameterization: two new inputs plus two new comparisons, and the sense of the existing comparison would have to change.
- `LegCountAtLeast` vs `TrendLegCountAboveMax` — different series (current pullback's legs off the settled bar counter) and a different reset; `HigherSwingLow.legs` is an ALL-OF floor on a run of known length, not a count that can be compared with "more than".
- `SpikeReversedBySpike` vs `OppositeLegsSimilarLength` — the bar-run form, no magnitude comparison, no pivots. A `similarityFraction` input on it would still be measuring bar runs.
- `SwingLegLengthAtLeast` vs `ExtensionLegExceedsSetupLeg` and vs `UpLegsLongerThanDownLegs` — that rule sizes the last two legs in BARS and puts a floor on each; both new rules compare leg PRICE magnitudes to each other. No input on a bar-count rule reaches a price comparison.
- `ExpandingTrianglePattern` vs `AscendingTriangleIntoLevel` — needs BOTH series diverging over five pivots; no setting holds one series flat.
- `HigherSwingLow` (with its new `legs`) vs `SwingTrendHigherHighsAndLows` — one series per side; neither a placement nor the negate toggle asks for both series on the same side.
- `ShrinkingSwingIncrementsExit` vs `SwingLegExceedsAverageLeg` — opposite sense, Exit vs Entry, and INCREMENTS on one series vs whole LEGS across both. A `sense` input would also have to change the quantity compared.
- `MicroTrendLineFailedBreakout` vs `MicroTrendLineReclaim` — the catalog rule needs the close to clear the POKING BAR's own extreme; this needs only the line. Considered as a `reclaimMode` input on the existing rule and rejected: the poke-tracking machinery differs (first-hit-with-extreme vs a flag), so the amendment would be a second code path, not an input.
- `TrendLineBrokenRecently` vs `TrendLineBreakConfirmedExit` — K-of-N over a window vs an ALL-OF-N run, and an Entry cannot sit in the exit pane, so no input on it can serve.
